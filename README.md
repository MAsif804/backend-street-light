# InLights Street Lights — Backend API

REST API for the Smart Street Lights dashboard. This document is the integration
reference for **firmware / hardware engineers** as well as app developers.

- **Stack:** [Hono](https://hono.dev) on [Bun](https://bun.sh), [Prisma 7](https://prisma.io), PostgreSQL
- **Local base URL:** `http://localhost:3000`
- **Content type:** `application/json` for all requests and responses

## 1. Quick start

```bash
bun install
```

Create `.env` (see [section 2](#2-environment-variables)), then:

```bash
bun run db:migrate      # apply migrations
bun run db:seed:geo     # cities / clusters / streets  (~2 min against a remote DB)
bun run db:seed         # device models, admin user, demo devices
bun run dev             # http://localhost:3000, hot reload
```

### Scripts

| Script | What it does |
|---|---|
| `bun run dev` | Dev server with hot reload |
| `bun run start` | Run once, no hot reload |
| `bun run db:generate` | Regenerate the Prisma client into `src/generated/prisma` |
| `bun run db:migrate` | `prisma migrate deploy` — apply existing migrations |
| `bun run db:migrate:dev` | `prisma migrate dev` — create a migration from schema changes |
| `bun run db:seed` | 3 device models, admin user, 7 gateways, 7 transformers, 6 lights, 1 schedule |
| `bun run db:seed:geo` | 132 cities, 268 clusters, 31 Islamabad streets |
| `bun run db:studio` | Prisma Studio — browse/edit the database in a GUI |

Both seeds are **idempotent** (upserts only), so re-running is safe.

> ⚠️ `db:seed:geo` is *authoritative* for Islamabad — it **deletes** any Islamabad
> cluster or street missing from its `ISLAMABAD_CLUSTER_MAPPING`. Devices are
> unaffected: they store `region`/`cluster` as plain strings, not foreign keys.

### Default login

Created by `db:seed`:

```
email:    admin@inlights.ai
password: InLights@321
```

Change this before exposing the API.

## 2. Environment variables

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | **Yes** | PostgreSQL connection string. Use the **pooled** endpoint when deploying serverless. |
| `JWT_SECRET` | **Yes** | Token signing key. Generate: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |
| `JWT_EXPIRES_IN_SECONDS` | No | Present in `.env` but **not read by the code** — expiry is hardcoded to `7d` in `src/lib/jwt.ts`. |

Copy `.env.example` to `.env` to start.

`DATABASE_URL` is resolved **lazily**, on the first query rather than at import
time (`src/lib/prisma.ts`). A missing value therefore produces a normal `500` on
the request that needed the database — with the cause in the logs — instead of
killing the process at startup. The client is cached on `globalThis` so warm
serverless invocations reuse one connection pool.

## 3. Data model

### Device hierarchy

```
Gateway ──< Transformer ──< Light
              │
              └──>< Schedule ──< Condition ──< TimePair
                    (many-to-many)

City ──< Cluster ──< Location        (reference data for UI dropdowns)
```

- A **Gateway** is the field hub and has many Transformers.
- A **Transformer** may belong to one Gateway (`gatewayId`, nullable) and has many Lights.
- A **Light** may belong to one Transformer (`transformerId`, nullable).
- A **Schedule** links to many Transformers.
- **Every relation is optional** — a device can exist unlinked.

> **Naming history:** the model now called `Transformer` was previously `Node`.
> Older firmware or docs referring to "node" / `nodeid` map to `Transformer` /
> `transformerId`.

### Two kinds of ID — this trips everyone up

Every device model has **both**:

| | Example | Used for |
|---|---|---|
| `id` — primary key | `cmscvxhy3000034uo061pr3lo` | **All URL paths**, all foreign keys |
| business key | `deviceId` / `transformerId` / `lightId` | The code printed on the hardware, e.g. `GW1CNST` |

`id` is a **cuid** generated by the database; business keys are yours and are
`@unique`. **URLs take `id`, not the business key.** The one exception is
`POST/PUT /lights`, which accepts either for `transformerId` ([7.5](#75-lights)).

There is no lookup-by-business-key endpoint. To resolve one, list and match:

```bash
curl -s http://localhost:3000/gateways | jq -r '.[] | select(.deviceId=="GW1CNST") | .id'
```

### Field reference

Timestamps are ISO 8601 strings (`2024-01-15T00:00:00.000Z`). `createdAt` and
`updatedAt` exist on every model and are managed automatically.

#### Gateway

| Field | Type | Notes |
|---|---|---|
| `id` | string (cuid) | primary key |
| `deviceId` | string | **required, unique** — hardware code |
| `name` | string | **required** |
| `status` | `ON` \| `OFF` | defaults `OFF` |
| `region` | string? | free text, e.g. `"Islamabad"` |
| `cluster` | string? | free text, e.g. `"Red Zone"` |
| `installationLocation` | string? | street |
| `latitude` / `longitude` | float? | decimal degrees |
| `voltage` | string? | display string, e.g. `"220V"` |
| `loadCapacity` | string? | e.g. `"100W"` |
| `powerRating` | string? | |
| `ipRating` | string? | e.g. `"IP65"` |
| `operationHours` | int | defaults `0` |
| `deviceConnected` | int | defaults `0` — **not auto-maintained**, see [section 12](#12-known-gaps-and-quirks) |
| `current` | string? | e.g. `"5.9 A"` |
| `lastActive` | datetime? | **never set by the server — write it yourself** |
| `installationDate` | datetime? | |
| `lastMaintenance` | datetime? | |
| `deviceModelId` | string? | FK → DeviceModel |

#### Transformer

Same as Gateway, **minus** `name`, `powerRating`, `current`, `deviceConnected`, **plus**:

| Field | Type | Notes |
|---|---|---|
| `transformerId` | string | **required, unique** — hardware code |
| `deviceId` | string? | optional secondary code |
| `gatewayId` | string? | FK → Gateway; `null` = unlinked |

#### Light

| Field | Type | Notes |
|---|---|---|
| `lightId` | string | **required, unique** |
| `name` | string | **required** |
| `status` | `ON` \| `OFF` | |
| `region`, `cluster` | string? | |
| `street` | string? | ⚠️ called `street` here, **not** `installationLocation` |
| `latitude` / `longitude` | float? | |
| `voltage`, `powerRating`, `ipRating` | string? | |
| `requiredCurrent` | string? | |
| `requiredCurrentVariation` | string? | |
| `operationHours` | int | |
| `current` | string? | |
| `lastActive`, `installationDate`, `lastMaintenance` | datetime? | |
| `transformerId` | string? | FK → Transformer |
| `deviceModelId` | string? | FK → DeviceModel |

#### DeviceModel

| Field | Type | Notes |
|---|---|---|
| `modelCode` | string | **required, unique**, e.g. `"SL-1234"` |
| `type` | `Light` \| `Transformer` \| `Gateway` | **required**, case-sensitive |
| `ipRating`, `voltage`, `powerRating`, `loadCapacity`, `reqCurrent` | string? | |

#### Schedule / Condition / TimePair

| Model | Field | Notes |
|---|---|---|
| Schedule | `name` | **required** |
| | `description` | string? |
| | `isActive` | bool, defaults `true` |
| | `conditions` | Condition[] |
| | `transformers` | Transformer[] (many-to-many) |
| Condition | `type` | `ON` \| `OFF`, defaults `ON` |
| | `years`, `months`, `days`, `hours`, `minutes` | int, default `0` — how long the schedule stays valid |
| | `timePairs` | TimePair[] |
| TimePair | `onTime` / `offTime` | string on a 12-hour clock, e.g. `"05:00"` |
| | `onPeriod` / `offPeriod` | `"AM"` \| `"PM"` |
| | `sortOrder` | int |

> Times are **strings on a 12-hour clock**, not timestamps, and there is no
> timezone field. Interpret them in the deployment's local time.

#### City / Cluster / Location

Reference data powering the UI's cascading dropdowns. `Cluster.name` is unique
within a city; `Location.name` is unique within a cluster. Deletes cascade
downward. **Devices do not reference these by foreign key** — `region` and
`cluster` on a device are plain strings, so deleting a cluster cannot orphan one.

## 5. Authentication

JWT bearer tokens, HS256, **7-day** expiry, payload `{ id, role }`.

```http
Authorization: Bearer <token>
```

### ⚠️ Almost nothing is actually protected

Only these require a token:

- `GET /auth/me`
- **all** `/users/*` routes

**Every device and scheduling endpoint is public** — `/gateways`, `/transformers`,
`/lights`, `/device-models`, `/schedules`, `/cities`, `/clusters`, `/locations`.
Anyone who can reach the API can read, create, modify and delete devices with no
credentials.

This makes firmware integration simple today — **your device does not need to log
in** — but the API must not be exposed publicly as-is. Before production, apply
`authMiddleware` to the device routes (or add a device-token middleware) and
issue firmware its own credential.

CORS is also wide open (`app.use("*", cors())` in `src/index.ts`). Pin it to your
dashboard's origin before deploying.

## 6. Request-handling rules you must know

These are the behaviours most likely to bite you from firmware.

### 6.1 POST and PUT coerce types — PATCH does not

`POST` and `PUT` on gateways / transformers / lights run every value through
coercion helpers, so **sending numbers as strings is fine**:

| Helper | Applies to | Behaviour |
|---|---|---|
| `toFloat` | `latitude`, `longitude` | `""` → unset; non-numeric → unset |
| `toInt` | `operationHours`, `deviceConnected` | truncates; `""` → unset |
| `toDate` | `lastActive`, `installationDate`, `lastMaintenance` | any `new Date()`-parsable string; invalid → unset |
| `toId` | `gatewayId`, `deviceModelId`, `transformerId` | `""`, `"-"`, whitespace → unset |

```jsonc
// POST / PUT — accepted and converted
{ "latitude": "33.7314", "operationHours": "1200", "lastActive": "2026-08-03T10:00:00Z" }
```

**`PATCH` is a raw pass-through straight to Prisma** — no coercion, no
validation. Send only real schema fields with correct JSON types:

```jsonc
{ "status": "ON", "latitude": 33.7314 }   // correct
{ "latitude": "33.7314" }                 // FAILS — string where Float expected
```

Use `PATCH` for cheap telemetry writes, `PUT` for full form updates.

### 6.2 Omitted vs. cleared

An omitted field is left **unchanged**. Because coercion maps `""` and `"-"` to
"unset", and unset means unchanged on `PUT`, **you cannot clear a field with an
empty string**. To explicitly null a foreign key, use `PATCH` with real `null`:

```bash
curl -X PATCH .../transformers/<id> -d '{"gatewayId": null}'   # unlink
```

### 6.3 Field aliases

Some endpoints accept alternative names because the web forms use different labels:

| Endpoint | Canonical | Also accepted |
|---|---|---|
| `POST /transformers` | `name` (validation only) | `deviceName`, `deviceId` |
| `POST /lights` | `lightId` | `deviceId` |
| `POST /lights` | `name` | `deviceName` |
| `POST/PUT /lights` | `street` | `installationLocation` |

### 6.4 Two surprising validation quirks

- **`POST /transformers` requires `name`, then discards it.** `Transformer` has no
  `name` column; the check is only a form guard. Send any non-empty value, e.g.
  `{"transformerId":"TR-01","name":"TR-01"}`.
- **`PUT /transformers/:id` cannot change `transformerId`** — it is not in the
  update payload. `PUT /gateways/:id` *can* change `deviceId`.

## 7. API reference

Routes are mounted in `src/index.ts`. There is **no `/api` prefix** — paths sit at the root.

### 7.1 Auth — `/auth`

| Method | Path | Auth | Body | Success |
|---|---|---|---|---|
| POST | `/auth/register` | — | `{ email, password, name?, role?, avatar? }` | `201` `{ user, token }` |
| POST | `/auth/login` | — | `{ email, password }` | `200` `{ user, token }` |
| GET | `/auth/me` | **Bearer** | — | `200` User |

`email` and `password` are required on both. Bad credentials or an inactive user →
`401 { "error": "Invalid credentials" }`. Duplicate email on register → `409`.
Passwords are bcrypt-hashed (cost 10) and never returned.

```bash
curl -X POST http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@inlights.ai","password":"InLights@321"}'
```

```jsonc
{
  "user": { "id": "cmsc...", "name": "Admin User", "email": "admin@inlights.ai",
            "role": "ADMIN", "avatar": null, "isActive": true },
  "token": "eyJhbGciOiJIUzI1NiIs..."
}
```

### 7.2 Users — `/users` *(every route requires Bearer)*

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/users` | — | `200` User[] |
| GET | `/users/:id` | — | `200` User |
| PUT | `/users/:id` | `{ name?, email?, role?, avatar?, isActive?, password? }` | `200` User |
| DELETE | `/users/:id` | — | `200` `{ message }` |

`password`, if sent, is re-hashed. `:id` must be a real cuid — **`/users/me` does
not work**; use `GET /auth/me`.

### 7.3 Gateways — `/gateways`

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/gateways` | — | `200` Gateway[] **+ `deviceModel`** |
| GET | `/gateways/:id` | — | `200` Gateway **+ `deviceModel`, `transformers[]`** |
| POST | `/gateways` | requires `deviceId`, `name` | `201` Gateway |
| PUT | `/gateways/:id` | any Gateway fields | `200` Gateway |
| PATCH | `/gateways/:id` | raw pass-through | `200` Gateway |
| DELETE | `/gateways/:id` | — | `200` `{ message }` |

```bash
curl -X POST http://localhost:3000/gateways \
  -H 'Content-Type: application/json' \
  -d '{
    "deviceId": "GW1CNST",
    "name": "Constitution Ave Hub",
    "status": "ON",
    "region": "Islamabad",
    "cluster": "Red Zone",
    "installationLocation": "Constitution Avenue",
    "latitude": "33.7314",
    "longitude": "73.0951",
    "voltage": "220V",
    "loadCapacity": "100W",
    "ipRating": "IP65"
  }'
```

Deleting a gateway sets its transformers' `gatewayId` to `null` (`onDelete: SetNull`) — the transformers survive.

### 7.4 Transformers — `/transformers`

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/transformers` | — | `200` Transformer[] **+ `gateway`, `deviceModel`** |
| GET | `/transformers/:id` | — | `200` **+ `gateway`, `deviceModel`, `lights[]`, `schedules[]`** |
| POST | `/transformers` | requires `transformerId` **and** `name` (discarded) | `201` |
| PUT | `/transformers/:id` | any fields **except `transformerId`** | `200` |
| PATCH | `/transformers/:id` | raw pass-through | `200` |
| DELETE | `/transformers/:id` | — | `200` `{ message }` |

Link and unlink from a gateway:

```bash
curl -X PATCH http://localhost:3000/transformers/<pk> \
  -H 'Content-Type: application/json' -d '{"gatewayId":"<gateway-pk>"}'

curl -X PATCH http://localhost:3000/transformers/<pk> \
  -H 'Content-Type: application/json' -d '{"gatewayId":null}'
```

### 7.5 Lights — `/lights`

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/lights` | — | `200` Light[] **+ `transformer`, `deviceModel`** |
| GET | `/lights/:id` | — | `200` Light + relations |
| POST | `/lights` | requires `lightId` (or `deviceId`) and `name` (or `deviceName`) | `201` |
| PUT | `/lights/:id` | any Light fields | `200` |
| PATCH | `/lights/:id` | raw pass-through | `200` |
| DELETE | `/lights/:id` | — | `200` `{ message }` |

**`transformerId` accepts either ID form.** POST/PUT resolve it by trying the
primary key first, then the business key. If neither matches it **silently links
nothing** rather than failing — a typo yields an orphaned light, not an error.
Always check that `transformer` is non-null in the response.

### 7.6 Device models — `/device-models`

| Method | Path | Body | Success |
|---|---|---|---|
| GET | `/device-models` | — | `200` DeviceModel[] |
| GET | `/device-models/:id` | — | `200` + `gateways[]`, `transformers[]`, `lights[]` |
| POST | `/device-models` | requires `modelCode`, `type` | `201` |
| PUT | `/device-models/:id` | | `200` |
| DELETE | `/device-models/:id` | — | `200` `{ message }` |

`type` is validated against `Light` / `Transformer` / `Gateway`; anything else
returns `400` listing the valid values.

### 7.7 Schedules — `/schedules`

| Method | Path | Behaviour |
|---|---|---|
| GET | `/schedules` | All schedules, newest first, with conditions (ordered by `createdAt`), time pairs (by `sortOrder`) and linked transformers |
| GET | `/schedules/:id` | One, same includes |
| POST | `/schedules` | Requires `name`. Creates nested conditions + time pairs. Links transformers via `transformerIds: string[]` (primary keys) |
| PUT | `/schedules/:id` | Full update. **Replaces** conditions and transformer links *only when those arrays are present* |
| PATCH | `/schedules/:id` | Scalars (`name`, `description`, `isActive`) and optionally `transformerIds`. **Never touches conditions** |
| DELETE | `/schedules/:id` | Cascade-deletes conditions + time pairs, unlinks transformers (devices untouched) |

```bash
curl -X POST http://localhost:3000/schedules \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Daily Scheduler",
    "description": "Everyday lighting schedule",
    "isActive": true,
    "transformerIds": ["<transformer-pk>"],
    "conditions": [{
      "type": "ON",
      "years": 0, "months": 1, "days": 0, "hours": 0, "minutes": 0,
      "timePairs": [
        { "onTime": "05:00", "onPeriod": "AM", "offTime": "07:00", "offPeriod": "AM", "sortOrder": 0 },
        { "onTime": "06:00", "onPeriod": "PM", "offTime": "11:00", "offPeriod": "PM", "sortOrder": 1 }
      ]
    }]
  }'
```

> `PUT` replaces conditions wholesale — it deletes every existing condition (and
> its time pairs) then recreates from your payload. Always send the **complete**
> set, or omit the key entirely to leave conditions alone.

### 7.8 Geography — `/cities`, `/clusters`, `/locations`

| Method | Path | Notes |
|---|---|---|
| GET | `/cities` | Alphabetical, each with `_count.clusters` |
| GET | `/cities/:id` | With clusters, each including its locations |
| POST / PUT / DELETE | `/cities`, `/cities/:id` | `{ name }`, unique |
| GET | `/clusters?cityId=<id>` | Filter by city; includes `city` and `_count.locations` |
| GET | `/clusters/:id` | With `city` and `locations[]` |
| POST / PUT / DELETE | `/clusters`, `/clusters/:id` | `{ name, cityId }` |
| GET | `/locations?clusterId=<id>` | Filter by cluster |
| GET | `/locations?cityId=<id>` | Filter by city (via the cluster's city) |
| POST / PUT / DELETE | `/locations`, `/locations/:id` | `{ name, clusterId }` |

## 8. Firmware integration guide

There is **no MQTT, CoAP, WebSocket or dedicated telemetry endpoint** in this
backend. Firmware integrates over plain HTTPS using the CRUD endpoints above.
See [section 12](#12-known-gaps-and-quirks) for what that implies.

### 8.1 Device lifecycle

**1 — Provisioning (once per device).** Register the hardware and store the
returned `id` (the cuid) in non-volatile memory. Every later call uses it in the
URL, so you never have to search again.

```bash
curl -X POST https://<api>/gateways \
  -H 'Content-Type: application/json' \
  -d '{"deviceId":"GW1CNST","name":"Constitution Ave Hub","status":"OFF"}'
# 201 -> { "id": "cmsc...", ... }   <-- persist this
```

Re-registering the same `deviceId` returns `409`. Treat that as "already
provisioned" and recover the `id` by listing and matching your hardware code:

```bash
curl -s https://<api>/gateways | jq -r '.[] | select(.deviceId=="GW1CNST") | .id'
```

**2 — Heartbeat.** Stamp `lastActive` yourself; the server never sets it.

```bash
curl -X PATCH https://<api>/gateways/<id> \
  -H 'Content-Type: application/json' \
  -d '{"lastActive":"2026-08-03T10:15:00.000Z"}'
```

**3 — Report state.** After driving a relay, write the new status back so the
dashboard reflects reality:

```bash
curl -X PATCH https://<api>/lights/<id> \
  -H 'Content-Type: application/json' \
  -d '{"status":"ON","current":"0.48 A","operationHours":1240}'
```

**4 — Read the schedule.** Poll and evaluate on-device:

```bash
curl -s https://<api>/transformers/<id> | jq '.schedules'
```

`GET /schedules` already embeds conditions, time pairs and linked transformers in
a single response, which is usually the cheaper call.

### 8.2 Minimal ESP32 / Arduino sketch

```cpp
#include <WiFi.h>
#include <HTTPClient.h>

const char* API        = "https://your-backend.vercel.app";
const char* GATEWAY_PK = "cmscvxhy3000034uo061pr3lo";  // stored at provisioning

void patchStatus(const char* status) {
  HTTPClient http;
  http.begin(String(API) + "/gateways/" + GATEWAY_PK);
  http.addHeader("Content-Type", "application/json");

  // PATCH does no coercion: numbers must be JSON numbers, not strings.
  String body = String("{\"status\":\"") + status + "\"}";

  int code = http.PATCH(body);
  if (code != 200) {
    Serial.printf("PATCH failed %d: %s\n", code, http.getString().c_str());
  }
  http.end();
}
```

No `Authorization` header is needed today. If the device routes are later
protected, add `http.addHeader("Authorization", "Bearer " + token);`.

### 8.3 Rules of thumb

- **Use `PATCH` for telemetry** — smallest payload, touches only what you send.
- **Send correct JSON types to `PATCH`** — `33.7314`, not `"33.7314"`. Strings are only coerced on POST/PUT.
- **`status` must be uppercase**: `"ON"` / `"OFF"`.
- **Timestamps must be ISO 8601 with a timezone**: `2026-08-03T10:15:00.000Z`.
- **Persist the cuid `id`** — recovering it means downloading the whole collection.
- **Expect `409` on re-registration** and treat it as success.
- **Check the response when creating a light** — a bad `transformerId` fails silently.
- **Back off on `5xx`** — a cold serverless start plus a database connection can take several seconds.

## 9. Error codes

All errors are JSON: `{ "error": "message" }`.

| Status | Meaning | Typical cause |
|---|---|---|
| `400` | Bad request | Missing required field, invalid enum, bad FK, wrong JSON type on `PATCH` |
| `401` | Unauthorized | Missing / malformed / expired token, or bad login |
| `404` | Not found | No record with that `id` |
| `409` | Conflict | Unique constraint — `deviceId` / `transformerId` / `lightId` / `modelCode` / `email` exists |
| `500` | Server error | Unhandled failure — check logs (a missing `DATABASE_URL` lands here) |

Underlying Prisma codes, surfaced as the statuses above:

| Prisma | Meaning |
|---|---|
| `P2002` | Unique constraint violated → `409` |
| `P2003` | Foreign key constraint failed → `400` |
| `P2025` | Record not found → `404` |

## 10. Docker

`docker-compose.yml` runs **Postgres only** — the API runs on the host with
`bun run dev`.

```sh
docker compose up -d
```

Postgres listens on `localhost:5432` with user `postgres`, database
`streetlights`, and data persisted in the `pgdata` volume. `DATABASE_URL` must
match:

```
DATABASE_URL="postgresql://postgres:517517@localhost:5432/streetlights?schema=public"
```

Apply migrations with `bun run db:migrate`.

### Building the API image

`Dockerfile` is multi-stage and independent of Compose. Build a stage with `--target`:

- `runtime` (default) — production image, non-root `bun` user, prod dependencies only, `HEALTHCHECK` on `GET /`.
- `dev` — full dependency tree and `bun run dev` (hot reload); bind-mount your working tree over `/app`.
- `migrate` — includes the Prisma CLI, runs `prisma migrate deploy`.

`prisma generate` runs during the build, so `src/generated/prisma` is baked into
the image and need not exist on the host.

```sh
docker build -t street-light-backend .
docker run --rm -p 3000:3000 \
  -e DATABASE_URL="postgresql://postgres:517517@host.docker.internal:5432/streetlights?schema=public" \
  -e JWT_SECRET=... \
  street-light-backend
```

## 11. Deployment

Deployed on **Vercel** via its Hono framework detection: Vercel looks for
`src/index.ts` and serves its `export default app`.

`vercel.json`:

```json
{ "bunVersion": "1.x" }
```

### Two things that will break the deploy if changed

**1 — The project must stay ESM.** Prisma 7's generated client uses
`import.meta.url`, which cannot exist in CommonJS. Both of these are required:

- `package.json` → `"type": "module"`
- `tsconfig.json` → `"module": "ESNext"`

Remove either and the function dies at cold start with `SyntaxError: Cannot use
'import.meta' outside a module`. **`bun run dev` will still work locally** — Bun
tolerates both formats — so this only surfaces in production. Verify after any
config change:

```bash
npx tsc -p tsconfig.json --outDir tmp-check --noEmit false
grep -c "require(" tmp-check/src/generated/prisma/client.js   # must print 0
```

**2 — `src/generated/prisma` is gitignored** and rebuilt on every deploy by the
`postinstall: prisma generate` hook. Never commit it.

**3 — Do not add a sub-daily `crons` entry to `vercel.json` on a Hobby plan.**
Vercel validates cron expressions at *deploy* time and rejects anything more
frequent than once a day on Hobby — it fails the whole build, so the API stops
updating entirely and the symptom is a stale deployment serving 404s for new
routes, not a cron-specific error. This bit us once: every deploy from
`46975d8` onward silently stopped landing. See "Running the schedule runner"
below for how to drive it without Vercel Cron.

### Running the schedule runner

`GET|POST /schedules/run` evaluates every active schedule and reconciles
`Transformer.status`. Nothing calls it on its own — it needs a trigger roughly
once a minute:

- **Vercel Cron (Pro only).** Add to `vercel.json`:
  ```json
  "crons": [{ "path": "/schedules/run", "schedule": "* * * * *" }]
  ```
- **Any external scheduler** (cron-job.org, GitHub Actions, an always-on box) —
  works on every plan:
  ```bash
  curl -X POST https://<host>/schedules/run -H "Authorization: Bearer $CRON_SECRET"
  ```

Set `CRON_SECRET` in the environment and the endpoint requires that bearer
token; leave it unset and the endpoint is open, like the other device routes.

### Environment variables on Vercel

Set `DATABASE_URL` and `JWT_SECRET` under Project Settings → Environment
Variables, **for the environment you deploy to** (Production and Preview are
separate). Changes require a redeploy.

### `sslmode` warning

If the connection string uses `sslmode=require`, `pg` prints a deprecation
warning with a stack trace on every cold start. It is **not an error**. Use
`sslmode=verify-full` to silence it and keep today's stronger behaviour. Do not
use `uselibpqcompat=true` — that opts into weaker semantics.

## 12. Known gaps and quirks

Plan around these when integrating hardware.

### Not implemented

- **No device authentication.** Device routes are fully public — see [section 5](#5-authentication).
- **No telemetry ingest or history.** Every write overwrites the current row. `current` and `operationHours` are snapshots, not time series.
- **No push channel.** No MQTT, WebSocket or SSE. Devices must **poll** for schedule changes; the server cannot command a device.
- **No bulk endpoints.** One HTTP request per device per update.
- **No pagination, filtering or sorting** on list endpoints, apart from the geography `?cityId` / `?clusterId` filters. `GET /lights` returns every light.
- **No rate limiting.**
- **No `/lookup/device-models` route**, despite a schema comment mentioning one — use `GET /device-models`.

### Behavioural quirks

- **`Gateway.deviceConnected` is not maintained by the server.** It holds whatever was last written. The dashboard ignores it and counts linked transformers instead.
- **`lastActive` is never set automatically** — firmware must write it.
- **`POST /transformers` requires `name` but discards it** (no such column).
- **`PUT /transformers/:id` silently ignores `transformerId`.**
- **A bad `transformerId` on `POST /lights` links nothing instead of erroring.**
- **`JWT_EXPIRES_IN_SECONDS` is ignored** — expiry is hardcoded to `7d`.
- **Transformers have no `current` field**, though gateways and lights do.
- **Schedule times are 12-hour strings with no timezone.**

### Before production

1. Put auth on the device routes and issue per-device credentials.
2. Pin CORS to the dashboard origin.
3. Rotate `JWT_SECRET` and keep `.env` out of git.
4. Change the seeded admin password.
5. Add pagination to list endpoints before device counts grow.
